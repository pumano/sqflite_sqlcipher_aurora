1. Сверены все десять основных замечаний и дополнительные утверждения исходного документа.
2. Собраны нативные проверки с настоящими `Database`, `AsyncQueue` и поставляемой x86_64-библиотекой SQLCipher.

Нативные результаты ниже получены на хосте x86_64. Проверки на физическом устройстве Aurora и ThreadSanitizer не запускались. Сценарии на Dart приведены для воспроизведения в приложении; отдельно указано, где вывод основан на анализе кода, а не на выполнении такого сценария на устройстве.

## 2. Основной вывод

Документ частично актуален. Он содержит реальные проблемы, но смешивает подтверждённые ошибки, ожидаемое удержание ресурсов, меры усиления защиты и предположения о многопоточности.

Особенно важны следующие поправки:

- Пункт 2 о потере handle в `close()` не соответствует коду.
- Пункт 7 о молчаливом игнорировании пароля для обычной БД опровергнут проверкой.
- Утечка `errmsg` существует, но обычный неверный пароль не вызывает её по описанному пути.
- Для single-instance неверно описано перезаписывание записи: используется `emplace`, который сохраняет первую запись.

## 3. Подробная проверка основных замечаний

### 3.1. Пункт 1: утечка `errmsg` в `setKey()`

**Вердикт: ошибка реальна, но утверждение «утекает при каждом неверном ключе» неверно.**

Источник: [`Database::setKey()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L124).

`sqlite3_exec()` может вернуть выделенный SQLite буфер сообщения об ошибке через `errmsg`. Плагин копирует текст в `utils::error`, но не освобождает сам буфер.

При обычном неверном пароле `PRAGMA key` успешно принимает пароль. Ошибка возникает позже, когда `validateOpenDatabase()` пытается прочитать БД. В этом сценарии буфер `errmsg` из `setKey()` не выделяется.

Реальный воспроизводимый случай — пароль с NUL. Внутри SQL-строки NUL обрывает переданную в SQLite строку до закрывающей кавычки. SQLite возвращает синтаксическую ошибку и выделяет `errmsg`.

**Результаты нативной проверки:**

```text
wrong password: rejected=1 exec_error_allocations=0
message=file is not a database (code 26)

NUL password: exec_error_allocations=100 retained_sqlite_bytes=3200
message=unrecognized token: "'prefix"
```

Число 3200 байт относится к конкретной проверке из 100 вызовов `setKey()` с искусственным паролем `prefix\0suffix`. Это не универсальный размер утечки для любого сообщения или платформы.

**Диагностический сценарий на Dart:**

```dart
import 'dart:io';
import 'package:sqflite_sqlcipher/sqflite.dart';

Future<void> reproduceInvalidPassword() async {
  final directory = await getDatabasesPath();
  final stamp = DateTime.now().microsecondsSinceEpoch;
  for (var i = 0; i < 100; i++) {
    final path = '$directory/nul_password_${stamp}_$i.db';
    try {
      final db = await openDatabase(path,
          password: 'prefix\u0000suffix', singleInstance: false);
      await db.close();
      throw StateError('Expected a password error');
    } on DatabaseException {
      // The current native implementation leaks the SQLite error buffer.
    } finally {
      final file = File(path);
      if (await file.exists()) await file.delete();
    }
  }
}
```

Этот Dart-сценарий не измеряет утечку самостоятельно. Для измерения нужны нативный счётчик выделений или профилировщик. Нативный сценарий выполнен; Dart-сценарий на устройстве не запускался.

**Исправление:**

1. Скопировать текст ошибки в владеющий строкой объект.
2. Освободить `errmsg` через `sqlite3_free()`.
3. Вернуть сохранённую ошибку.
4. Отдельно определить поддержку паролей с NUL: передавать пароль через API с явной длиной либо явно отклонять такой ввод.

Нельзя просто освободить `errmsg` перед существующим `return`, сохранив `const auto message`: сейчас это указатель, и такое изменение создаст обращение к освобождённой памяти.

### 3.2. Пункт 2: потеря handle при ошибке `close()`

**Вердикт: описанной ошибки в проверенном коде нет.**

Источник: [`Database::close()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L215).

При ошибке `sqlite3_close_v2()` функция сразу возвращает `utils::error`. Присваивание `db_ = nullptr` находится после этой проверки и выполняется только при успешном закрытии.

Следовательно, предложение «не обнулять `db_` при ошибке» уже соответствует текущему поведению. Возможные вопросы к обработке ошибки закрытия в деструкторе нужно исследовать отдельно; они не доказывают описанную в документе потерю указателя.

### 3.3. Пункт 3: заброшенные курсоры

**Вердикт: удержание ресурсов подтверждено, но отсутствие TTL не является самостоятельным доказательством ошибки API.**

Источники: [`queryWithPageSize()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L363), [`closeCursor()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L661).

Пока курсор не исчерпан, не отменён или не закрыта БД, его statement остаётся в `cursors_`. В проверенном Dart-классе `SqfliteQueryCursor` автоматического finalizer для нативного курсора нет.

Нативная проверка создала десять частично прочитанных курсоров: в таблице осталось десять statements. После `Database::close()` таблица очистилась, statements были финализированы.

Для раннего выхода из чтения потребитель должен закрывать курсор в `finally`:

```dart
import 'package:sqflite_sqlcipher/sqflite.dart';

Future<void> readFirstRow(Database db) async {
  final cursor = await db.rawQueryCursor('SELECT * FROM t', null,
      bufferSize: 1);
  try {
    if (await cursor.moveNext()) {
      final row = cursor.current;
      print(row);
    }
  } finally {
    await cursor.close();
  }
}
```

**Что улучшать:** документировать обязательное закрытие при раннем выходе, показывать `try/finally` в примере и при необходимости добавить диагностику количества активных курсоров. Лимиты могут быть полезны, но TTL способен неожиданно закрыть легитимный медленный курсор и требует отдельного проектирования.

### 3.4. Пункт 4: очередь команд и потеря ответов при закрытии

**Вердикт: подтверждено. Это одна из приоритетных проблем отчёта.**

Источники: [`processSqlCommand()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L448), [`close()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L215).

Если активна чужая транзакция, команда помещается в `pendingSqlCallbacks_`. Ограничения размера очереди нет. Если транзакция не завершается из-за логической ошибки потребителя, callbacks продолжают удерживать аргументы, результаты вызовов и другие захваченные объекты.

При успешном закрытии БД очередь сбрасывается присваиванием пустого контейнера. Для ожидающих команд не вызывается `MethodResult::Error()`.

Нативная проверка показала:

```text
close pending: queued_before=1 responses=0 result_destroyed=1 cursors_after=0
```

Дополнительно проверен `ReplyManager` в `aurora_client_wrapper 1.14.0`: его деструктор при отсутствии ответа только печатает предупреждение. Он намеренно не отправляет автоматический ответ, поскольку движок к этому моменту уже может быть недействителен. Следовательно, уничтожение `MethodResult` не завершает Dart Future.

**Диагностический сценарий через настоящий method channel:**

```dart
import 'dart:async';
import 'package:flutter/services.dart';

Future<void> reproduceDroppedPendingReply() async {
  const channel = MethodChannel('com.davidmartos96.sqflite_sqlcipher');
  final opened = await channel.invokeMapMethod<String, Object?>(
      'openDatabase', {'path': ':memory:', 'singleInstance': false});
  final id = opened!['id'] as int;
  await channel.invokeMethod<Object?>('execute', {
    'id': id,
    'sql': 'BEGIN IMMEDIATE',
    'inTransaction': true,
    'transactionId': null,
  });

  // No transactionId: the native plugin queues this command.
  final pending = channel.invokeMethod<void>(
      'execute', {'id': id, 'sql': 'SELECT 1'});
  await channel.invokeMethod<void>('closeDatabase', {'id': id});
  try {
    await pending.timeout(const Duration(seconds: 2));
    throw StateError('Expected a missing native reply');
  } on TimeoutException {
    // The native close discarded the command without replying.
  }
}
```

Прямой канал нужен, чтобы проверить нативную очередь независимо от блокировок `sqflite_common`. Обычный Dart API может сериализовать вызовы раньше, в том числе не позволить `close()` пройти за ожидающей операцией. Нативная потеря ответа подтверждена; этот Dart-сценарий на устройстве не запускался.

**Исправление:**

1. Хранить у ожидающей команды не только callback выполнения, но и явный способ завершить её ошибкой.
2. При закрытии сначала запретить приём новых команд, затем завершить ожидающие команды ошибкой `database closed`.
3. Обеспечить ровно один ответ на каждый method call.
4. Отдельно определить предел очереди и поведение при перегрузке. Добавление таймаута только на Dart-стороне не удалит уже захваченные нативные callbacks.

### 3.5. Пункт 5: проглатывание исключений в `executeTasks()`

**Вердикт: подтверждено. Проблема не ограничена нехваткой памяти.**

Источник: [`AsyncQueue::executeTasks()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/async_queue.cpp#L47).

Любое исключение из задачи попадает в пустой `catch (...)`. Если задача не успела ответить, результат вызова уничтожается без ответа.

Вместо искусственного `bad_alloc` проверен обычный файловый сбой: удаление непустого каталога через бросающий исключения вариант `std::filesystem::remove()`. Следующая задача выполняется, но первая не отвечает:

```text
throwing remove in AsyncQueue: later_task_ran=1 responded=0
```

**Диагностический Dart-сценарий:**

```dart
import 'dart:async';
import 'dart:io';
import 'package:sqflite_sqlcipher/sqflite.dart';

Future<void> reproduceSwallowedFilesystemError() async {
  final path = '${await getDatabasesPath()}/invalid_delete_'
      '${DateTime.now().microsecondsSinceEpoch}';
  final directory = await Directory(path).create(recursive: true);
  await File('$path/entry').writeAsString('not a database');
  try {
    await deleteDatabase(path).timeout(const Duration(seconds: 2));
  } on TimeoutException {
    // Invalid input should produce an error, rather than no reply.
  } finally {
    await directory.delete(recursive: true);
  }
}
```

Вход намеренно некорректен: удалению передан непустой каталог. Это проверка корректного ответа при ошибке, а не поддерживаемый способ удалить БД. Аналогичный путь возможен при реальных файловых исключениях. Нативный сценарий выполнен; Dart-сценарий на устройстве не запускался.

**Исправление:** добавить границу обработки исключений, которая сохраняет доступ к `MethodResult` и завершает вызов ошибкой. Логирование полезно для диагностики, но само по себе зависший Future не исправляет. Для `std::filesystem` также можно использовать варианты с `std::error_code`, после чего явно преобразовывать ошибку в ответ канала.

### 3.6. Пункт 6: пароль в памяти и передача через SQL

**Вердикт: актуальная мера усиления защиты; конкретный дефект с NUL подтверждён.**

Источники: [`onOpenDatabaseCall()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L198), [`setKey()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L124).

Плагин копирует пароль в `std::string`, захватывает его в асинхронную задачу и собирает ещё одну строку с `PRAGMA key`. Явного затирания этих буферов нет.

Терминологически следует различать пользовательский пароль и производный ключ шифрования внутри SQLCipher. В данном участке плагина речь прежде всего о копиях пароля и его SQL-представления.

Удвоение одинарных кавычек обеспечивает корректное экранирование обычной SQL-строки. Но NUL обрывает строку на границе `c_str()`. Проверенный результат — синтаксическая ошибка, содержащая префикс искусственного пароля: `unrecognized token: "'prefix"`.

Это уточняет и положительное утверждение «ключ не попадает в логи»: штатное логирование `setKey()` действительно не печатает пароль напрямую, но возвращаемая ошибка может содержать его часть. Если приложение журналирует исключение целиком, эта часть может оказаться в журнале.

**Исправление:**

1. Рассмотреть `sqlite3_key_v2()` с явной длиной: это устраняет необходимость SQL-строки и позволяет корректно передать NUL.
2. Для использования декларации проверить определение `SQLITE_HAS_CODEC` при компиляции плагина и соответствие вендоренному заголовку/библиотеке.
3. Уменьшить число копий пароля и обеспечить безопасное затирание принадлежащих нативному коду буферов, когда они больше не нужны.
4. Не возвращать пользователю текст SQL с паролем внутри сообщения об ошибке.
5. Если поддержка NUL не планируется, явно валидировать ввод и возвращать нейтральную ошибку без пароля.

Затирание одной локальной строки не даёт гарантии удаления всех копий: остаются другие нативные строки, сериализованное сообщение и Dart-объекты. В отчёте такую меру нельзя описывать как полное решение защиты памяти.

### 3.7. Пункт 7: пароль на незашифрованную БД

**Вердикт: утверждение опровергнуто для проверенной версии.**

Источник: [`open()` и `openReadOnly()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L150).

После установки пароля плагин проверяет доступность БД реальным чтением `PRAGMA user_version`. Существующий обычный SQLite-файл не проходит проверку с заданным паролем.

```text
plain DB with password: rejected=1
message=file is not a database (code 26)
plain DB remains readable=1
```

Предложение добавить проверку `PRAGMA cipher` не соответствует причине: этот pragma не заменяет проверку чтения и не доказывает, что существующий файл успешно расшифрован. В коде SQLCipher он возвращает сведения об алгоритме при наличии cipher-контекста, а не результат проверки аутентичности файла.

**Dart-сценарий для проверки поведения:**

```dart
import 'package:sqflite_sqlcipher/sqflite.dart';

Future<void> verifyPlainDatabaseRejectsPassword() async {
  final path = '${await getDatabasesPath()}/plain_'
      '${DateTime.now().microsecondsSinceEpoch}.db';
  var db = await openDatabase(path, singleInstance: false);
  await db.execute('CREATE TABLE t(v TEXT)');
  await db.insert('t', {'v': 'plain'});
  await db.close();
  try {
    db = await openDatabase(path,
        password: 'some-password', singleInstance: false);
    await db.close();
    throw StateError('Expected an error for a plain database with a key');
  } on DatabaseException {
    // Expected on the current native implementation.
  }
  db = await openDatabase(path, singleInstance: false);
  try {
    final rows = await db.query('t');
    if (rows.single['v'] != 'plain') throw StateError('Data changed');
  } finally {
    await db.close();
    await deleteDatabase(path);
  }
}
```

Открытие обычной БД с паролем также не является способом зашифровать существующий файл: для миграции нужен отдельный, явно спроектированный процесс. Ошибка обычного открытия не означает, что файл был преобразован или повреждён.

### 3.8. Пункт 8: гонки доступа к состоянию БД

**Вердикт: несинхронизированный доступ подтверждается по коду. Формулировку и исправление нужно уточнить.**

Источники: [`onOpenDatabaseCall()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L198), [`Database::close()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/database.cpp#L215).

В потоке канала обработчик повторного single-instance открытия читает `db->isOpen()` и `db->isInTransaction()`. Worker меняет `db_` и состояние транзакции. Между этими чтениями и записями общей синхронизации нет.

Mutex защищает поиск в картах и изменение карт. После возврата из `databaseByPath()` он уже освобождён и не защищает дальнейшее чтение полей `Database`.

При этом `onDebugCall()` в проверенной версии `db_` не читает — это место в исходном документе указано неточно.

**Исправление:** предпочтительно выполнять проверки состояния и повторное открытие в том же worker, который владеет SQLite-соединением. Альтернатива — явно определить общую синхронизацию состояния и всех его читателей/писателей. Замена только `db_` на атомарный указатель не исправит доступ к состоянию транзакции и всю последовательность «проверить — использовать».

Динамический отчёт ThreadSanitizer не получен: вердикт основан на анализе доступов и отсутствия синхронизации. Простое многократное выполнение Dart-кода без сбоя не опровергает такую гонку.

### 3.9. Пункт 9: конкурентное single-instance открытие

**Вердикт: окно гонки в нативном обработчике есть, но сценарий и поведение карты описаны неточно.**

Источники: [`onOpenDatabaseCall()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L198), [`databaseAdd()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L651).

Возможная последовательность:

1. Первый обработчик не находит БД по пути и ставит открытие в worker.
2. Пока открытие не завершено и `databaseAdd()` не выполнен, второй обработчик тоже не находит БД.
3. Создаются два `Database` с разными ID, затем оба открываются.
4. `singleInstanceDatabases_.emplace()` сохраняет первую запись, а не перезаписывает её второй.
5. В `databases_` при этом могут находиться оба ID. Контракт одного нативного соединения для пути не обеспечен этим обработчиком.

Обычные `openDatabase()` одного экземпляра Dart factory защищены блокировкой по пути в `sqflite_common`. Поэтому два вызова из одного isolate через стандартный API не являются достаточным воспроизведением. Нужны разные isolate с независимыми фабриками или прямые обращения к каналу.

**Диагностический сценарий для нативного обработчика:**

```dart
import 'package:flutter/services.dart';
import 'package:sqflite_sqlcipher/sqflite.dart' as sqlcipher;

Future<void> probeNativeSingleInstanceOpen() async {
  final path = '${await sqlcipher.getDatabasesPath()}/open_race_'
      '${DateTime.now().microsecondsSinceEpoch}.db';
  final seed = await sqlcipher.openDatabase(path,
      password: 'review-password', singleInstance: false);
  await seed.execute('CREATE TABLE t(v TEXT)');
  await seed.close();

  const channel = MethodChannel('com.davidmartos96.sqflite_sqlcipher');
  final args = <String, Object?>{
    'path': path,
    'password': 'review-password',
    'singleInstance': true,
  };
  final results = await Future.wait([
    channel.invokeMapMethod<String, Object?>('openDatabase', args),
    channel.invokeMapMethod<String, Object?>('openDatabase', args),
  ]);
  final ids = results.map((r) => r!['id'] as int).toSet();
  for (final id in ids) {
    await channel.invokeMethod<void>('closeDatabase', {'id': id});
  }
  await sqlcipher.deleteDatabase(path);
  if (ids.length != 1) {
    throw StateError('Multiple native IDs for a single-instance path: $ids');
  }
}
```

Сценарий обходит клиентскую сериализацию намеренно. Его проявление зависит от порядка обработки сообщений и времени открытия; на устройстве он не запускался. Для детерминированной регрессии нужен стенд, который задерживает первый open до прихода второго запроса.

**Исправление:** перенести всю последовательность поиска/открытия/регистрации в worker либо резервировать путь и объединять ожидающие открытия в одну операцию. Для корректности удаления записей также следует учитывать, какому ID принадлежит запись пути.

### 3.10. Пункт 10: удаление WAL, SHM и journal

**Вердикт: отсутствие явной очистки побочных файлов подтверждено; последствия зависят от состояния соединений.**

Источник: [`onDeleteDatabaseCall()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L285).

Обработчик удаляет основной путь. Он не перечисляет `-wal`, `-shm` и `-journal`. При штатном закрытии последнего SQLite-соединения часть этих файлов обычно удаляется SQLite самостоятельно, поэтому остатки нельзя обещать при каждом вызове.

Нативная проверка аварийного случая:

1. Дочерний процесс открывает SQLCipher-БД с паролем.
2. Включает WAL, создаёт таблицу и записывает данные.
3. Завершается через `_exit()` без закрытия БД.
4. Родитель выполняет удаление только основного файла, соответствующее текущему файловому действию обработчика.
5. Проверяет наличие WAL/SHM.

```text
unclean WAL delete: before_wal=1 before_shm=1 remaining_wal=1 remaining_shm=1
```

Это подтверждает остаточные файлы после аварии. Проверка не утверждает, что данные WAL стали незашифрованными или что таким способом обходится пароль.

**Исправление:** определить политику удаления всего набора файлов БД, предварительно обеспечив отсутствие активных соединений. Нельзя безусловно удалять WAL работающей БД. Нужно учитывать и соединения, открытые с `singleInstance: false`, которые не представлены в карте single-instance путей.

Утверждение «результат `remove()` не проверяется» следует уточнить: используемый overload бросает исключение при файловой ошибке. Возврат `false` может означать, что файла уже нет, что допустимо для идемпотентного удаления. Основной дефект обработки исключения описан в пункте 5.

## 4. Дополнительные утверждения исходного документа

### 4.1. Скобка в сообщении об ошибке

Источник: [`formatError()`](https://github.com/pumano/sqflite_sqlcipher_aurora/blob/b7fe5b3f1f17ead172e5104a8107d94a78ee9004/aurora/plugin.cpp#L666) и вызовы с описанием `ID=...`.

В документе направление ошибки перепутано. `formatError()` сам оборачивает описание в скобки, а вызывающий код уже добавляет закрывающую `)`. Получается лишняя скобка, например `database closed (ID=1))`. Это косметический дефект.

### 4.2. Недостающие SQL-параметры

Недостающие параметры действительно могут становиться SQL NULL. Но это относится и к `execute()`, а не только к `query()` и курсорам.

Нативные результаты:

```text
execute missing argument: error=0 missing_value_is_null=1
query missing argument: missing_value_is_null=1
```

В `execute()` есть проверка, что переданные аргументы вообще были связаны с каким-либо выражением. Это не равнозначно проверке `число аргументов == число параметров`. Лишние аргументы могут приводить к ошибке связывания, а недостающие остаются несвязанными и имеют обычное для SQLite значение NULL.

Если API должен отвергать несовпадение количества аргументов, такую проверку нужно явно определить и реализовать во всех путях. Для `execute()` необходимо учитывать поддержку нескольких SQL-выражений: простое сравнение с количеством параметров только первого выражения может быть неверным.

### 4.3. Блокирующий `filesystem::exists()`

Факт подтверждается: `onDatabaseExistsCall()` выполняет синхронную файловую операцию в потоке канала. Это потенциальная задержка, особенно на медленном файловом пути. По имеющимся данным ей нельзя приписать измеренное зависание UI или высокий приоритет: такие измерения не выполнялись.

### 4.4. Уничтожение `AsyncQueue` одновременно с `push()`

В классе нет завершённого протокола отклонения новых задач при shutdown. Однако доказать конкретный use-after-free только по этому фрагменту нельзя: нужно установить, допускает ли жизненный цикл движка/регистратора новый вызов после начала уничтожения плагина.

Статус — требует отдельного исследования. Нужны гарантии жизненного цикла `client_wrapper`, тест shutdown и, по возможности, проверка инструментами обнаружения ошибок памяти/потоков. Это не следует выдавать за уже воспроизведённую ошибку.

### 4.5. Положительные выводы документа

В проверенном `main` действительно присутствуют исправления сохранения TEXT с NUL, различения NULL и пустого BLOB, освобождения expanded SQL, сохранения файла при ошибке открытия и финализации курсоров в `close()`.

Нужно уточнить два утверждения:

- **`SQLITE_TEMP_STORE=2`** задаёт хранение временных структур в памяти по умолчанию, но допускает переключение на файл через `PRAGMA temp_store=FILE`. Это не жёсткий запрет дисковых temp-файлов. В SQLite вариант `SQLITE_TEMP_STORE=3` фиксирует хранение в памяти независимо от pragma.
- **«Ключ не попадает в логи»** корректно описывает отсутствие прямого штатного логирования в `setKey()`, но не исключает утечку префикса пароля через текст ошибки с NUL. Этот случай описан в пункте 6.

## 5. Предлагаемый порядок исправлений

### Первая очередь: завершение асинхронных вызовов

Пункты 4–5: гарантировать ответ на каждую принятую команду, включая закрытие БД, отмену и исключения. Это устраняет зависшие Future и делает ошибки диагностируемыми. После этого определить ограничения очереди и поведение при перегрузке.

### Вторая очередь: владение состоянием БД и конкурентное открытие

Пункты 8–9: выполнять проверки состояния и открытие в одном worker либо ввести полноценную синхронизацию и резервирование пути. Проверять отдельно один isolate, несколько isolate и прямые обращения к каналу.

### Третья очередь: обработка пароля и сообщения об ошибках

Пункты 1 и 6: освободить `errmsg`, убрать пароль из SQL-строки или явно валидировать NUL, не допускать попадания фрагментов пароля в диагностические сообщения. Исправление утечки небольшое и может выполняться независимо от более крупных изменений.

### Далее: ресурсы и удаление файлов

- Пункт 10: безопасно удалять полный набор файлов закрытой БД, включая остатки после аварии.
- Пункт 3: документировать раннее закрытие курсоров и добавить диагностику активных ресурсов.
- Определить желаемый контракт проверки SQL-аргументов и исправить форматирование сообщений.

Пункты 2 и 7 не требуют исправления в описанном виде. Гипотеза о shutdown должна оставаться отдельной задачей исследования до подтверждения.

## 6. Сводка выполненных нативных проверок

```text
wrong password: rejected=1 exec_error_allocations=0
message=file is not a database (code 26)

plain DB with password: rejected=1
message=file is not a database (code 26)
plain DB remains readable=1

NUL password: exec_error_allocations=100 retained_sqlite_bytes=3200
message=unrecognized token: "'prefix"

execute missing argument: error=0 missing_value_is_null=1
query missing argument: missing_value_is_null=1

abandoned cursor statements=10
close pending: queued_before=1 responses=0 result_destroyed=1 cursors_after=0

unclean WAL delete: before_wal=1 before_shm=1 remaining_wal=1 remaining_shm=1

throwing remove in AsyncQueue: later_task_ran=1 responded=0
```

Здесь `result_destroyed=1` означает уничтожение объекта результата без вызова его обработчиков, а не успешную отправку ответа. `remaining_wal=1` и `remaining_shm=1` означают наличие файлов после удаления основного пути. Счётчик утечки относится к выделениям SQLite в конкретном нативном сценарии.

Отчёт оценивает актуальность исходного аудита и не утверждает, что выполнен полный аудит безопасности плагина, SQLCipher, OpenSSL или среды исполнения.
